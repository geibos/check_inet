# Дизайн: адаптивная диагностика `check_inet`

Дата: 2026-07-11
Статус: утверждён (ожидает финального ревью спеки)

## Цель

Расширить `check_inet` до полноценной диагностики: один бинарь, запускаемый при
неполадках, определяет, **на каком этапе** ломается связность. Быстрый в здоровом
случае (early-return), полный разбор — только при проблеме. Диагностика выполняется
параллельно, результаты интерпретируются как лесенка зависимостей (корень = первый
упавший этап). Стек остаётся минимальным (std + ureq), без новых зависимостей.

## Управляющий поток (адаптивный)

Диагностика — поведение по умолчанию, с early-return:

1. **Фаза 1 (быстрая):** параллельно `gateway` + `internet-by-IP` + `application`
   (HTTPS/TCP до target), печать строк, retry по `--times`/`--delay` (как сейчас).
2. Если на какой-либо попытке все три зелёные → **exit 0** (сегодняшнее поведение).
3. Если после всех попыток провал → **эскалация:** печать разделителя
   `--- диагностика ---`, параллельный прогон дополнительных проб (локальный IP,
   глубокий DNS, captive portal, IPv6), вычисление лесенки, печать **вердикта**,
   `exit = номер этапа`.

Здоровый случай платит только за фазу 1. Тяжёлые пробы — лишь при проблеме.

## Лесенка и exit codes

Корень = первый упавший этап снизу вверх:

| exit | Stage | Проба |
|---|---|---|
| 0 | — (здорово) | — |
| 1 | LocalIp — нет локального IP (линк/DHCP) | UDP-connect + `local_addr` |
| 2 | Gateway — шлюз недостижим | reachability до шлюза |
| 3 | Internet — нет выхода в интернет (маршрут/ISP) | reachability до публичного IP |
| 4 | Dns — DNS не работает | ручной UDP-запрос к системным + публичным |
| 5 | Application — TLS/HTTP до цели | HTTPS/TCP до target |
| 6 | CaptivePortal — сеть требует авторизации | generate_204 |

- `Stage` — enum со значениями 1..6; exit code = `Stage as u8`, либо 0 если здорово.
- **CaptivePortal имеет приоритет:** если портал обнаружен, вердикт = CaptivePortal,
  даже если линейно первым падает Application (портал — актуальная причина).
- **IPv6 — информационно:** печатается строка со статусом, на вердикт/exit не влияет
  (сети без IPv6 — норма).

## Reachability ≠ порт открыт

`Connection refused` доказывает, что хост жив (ответил RST). Классификация исхода
TCP-connect (чистая функция от `io::ErrorKind`, тестируемая):

- **Достижим:** `Ok` | `ConnectionRefused` | `ConnectionReset`.
- **Недостижим:** `TimedOut` | `NetworkUnreachable` | `HostUnreachable` | прочее.

Этапы Gateway и Internet используют reachability (хост ответил = этап пройден). Это
устраняет ложный «шлюз недоступен», когда роутер просто не слушает порт 80.

## Глубокий DNS (без зависимостей)

- **Определение системных серверов:**
  - Linux — строки `nameserver <IP>` из `/etc/resolv.conf`.
  - macOS — `scutil --dns`, строки `nameserver[N] : <IP>`.
  - Чистые парсеры `parse_resolv_conf` / `parse_scutil` на фикстурах.
- **Ручной DNS-по-UDP:**
  - `build_query(name, id) -> Vec<u8>`: 12-байтовый заголовок (ID, flags `0x0100`
    = recursion desired, QDCOUNT=1, остальные 0) + QNAME (label-префиксы, терминатор 0)
    + QTYPE=1 (A) + QCLASS=1 (IN).
  - I/O: `UdpSocket::bind("0.0.0.0:0")`, `set_read_timeout(3s)`, `send_to(server:53)`,
    `recv_from`.
  - `parse_response(buf, expected_id) -> DnsAnswer`: проверка ID, бит QR, `RCODE`
    (`flags[3] & 0x0F`), `ANCOUNT` (байты 6-7).
- **Классификация исходов** (чистая функция от результатов запросов к системным и
  публичным серверам):
  - Системный отвечает (RCODE=0, ANCOUNT>0) → DNS ок.
  - Системный молчит/ошибка, публичный (8.8.8.8/1.1.1.1) отвечает → «ваш DNS сломан,
    публичные работают».
  - Все таймаут → «:53 заблокирован / DNS недоступен».
  - Все NXDOMAIN (RCODE=3) → имя не существует (опечатка в target).
- **Заметка:** при systemd-resolved `nameserver` часто `127.0.0.53` — запрос к нему
  тестирует локальный stub-резолвер, это валидно. Разбор upstream через `resolvectl`
  — вне области (см. YAGNI).

## Аргумент target

Необязательный позиционный `host[:port]`. Парсер `Target` (чистая функция):

- `parse::<SocketAddr>()` → IP + порт.
- иначе `parse::<IpAddr>()` → IP + порт 443.
- иначе `host[:port]` (rsplit по `:` только если суффикс — валидный порт и в хосте нет
  `:`) → Host + порт, либо весь ввод как Host + 443.
- IPv6 c портом — через скобочную форму `[::1]:443` (её понимает `SocketAddr`).

Поведение по типу:
- **Host** → участвует в DNS-этапе + TCP/HTTPS до него; порт по умолчанию 443.
- **IP** → DNS-этап для цели пропускается; TCP:443 до него (без HTTPS).
- **Без аргумента** — дефолт: `ya.ru` (Application/HTTPS), `8.8.8.8` (Internet-by-IP).

## Пробы (детали, всё на std + ureq)

- **local-ip:** `UdpSocket::bind("0.0.0.0:0")` + `connect(<target/8.8.8.8>:80)` +
  `local_addr()`. Пакеты не шлются (UDP connect только задаёт peer и выбирает
  src-адрес по таблице маршрутизации). Ошибка/`unspecified` → нет локального IP.
- **gateway:** `gateway::detect()` (есть) + reachability-проба TCP до `<gw>:80`.
- **internet-by-IP:** reachability TCP до `8.8.8.8:443` — якорь «интернет вообще жив»,
  всегда фиксированный публичный IP (не target). Сам target проверяется на этапе
  Application.
- **application:** для Host — HTTPS через `ureq` (как сейчас); для IP — TCP:443.
- **captive-portal:** `ureq` GET `http://connectivitycheck.gstatic.com/generate_204`
  с **отключёнными редиректами**; ожидание 204 + пустое тело. Любой иной ответ (200 с
  телом, редирект) → портал. Обязательно plain HTTP (порталы перехватывают HTTP). API
  отключения редиректов у `ureq` уточнить при имплементации.
- **ipv6:** `connect_timeout` до `[2001:4860:4860::8888]:443` (reachability,
  информационно).

`TIMEOUT` = 3с (как сейчас).

## Формат вывода

Строки проверок — прежний `row()`. При эскалации после проб — вердикт:

```
--- диагностика ---
192.168.1.42  | 🟢 | 0.0003
192.168.1.1   | 🟢 | 0.0210
8.8.8.8       | 🛑 | 3.0001 | Timeout
...
корень: [3] нет выхода в интернет — публичный IP недостижим (timeout), шлюз жив → маршрут/ISP
```

## Модули

```
src/
├── main.rs      — CLI (target + --times/--delay), адаптивный поток, exit codes
├── target.rs    — NEW: разбор Target (host[:port] / IP)
├── check.rs      — CheckOutcome + row() (есть); + хелпер форматирования вердикта
├── net.rs        — NEW: reachability-классификация, local-ip (UDP-трюк), ipv6-проба
├── checks.rs     — эволюция: пробы gateway / internet-ip / tls-http / captive-portal
├── dns.rs        — NEW: детект резолверов + DNS-по-UDP (build/parse) + проба + классификация
├── gateway.rs   — детект шлюза (есть)
└── diag.rs       — NEW: enum Stage, интерпретация лесенки, run_diagnostics (параллельно), вердикт + маппинг exit
```

Файлы держим фокусными (<400 строк).

## Тестирование (TDD на чистой логике)

- `target.rs`: `host`, `host:port`, `IP`, `IP:port`, `[ipv6]:port`, мусор.
- `net.rs`: reachability-классификация (refused→up, timeout→down, прочее→down).
- `dns.rs`: `build_query` (байтовый layout), `parse_response` (RCODE/ANCOUNT/ID-mismatch/
  QR-бит), `parse_resolv_conf`, `parse_scutil`, классификация исходов.
- `diag.rs`: `root_cause` (наборы исходов проб → корневой Stage; приоритет CaptivePortal;
  здоровый → None), `Stage`→exit.
- Сетевые пробы и I/O DNS — glue, проверяются реальным прогоном.

## Порядок имплементации (фазы для плана)

1. `net`: reachability-классификация + рефактор существующих проб под неё.
2. `target`: разбор аргумента.
3. `diag`: `Stage`, `root_cause`, адаптивный поток в `main`, exit codes (на уже
   имеющихся пробах фазы 1).
4. `dns`: определение резолверов + DNS-по-UDP + классификация.
5. `captive-portal` + `local-ip` + `ipv6`, подключение в лесенку.

Каждая фаза — RED→GREEN на чистой логике; в конце — реальный прогон бинарника.

## Вне области (YAGNI)

- Разбор upstream systemd-resolved через `resolvectl`.
- ICMP-ping (нужны привилегии/raw-сокеты) — reachability делаем по TCP.
- Конфигурируемые таймаут/публичные DNS/captive-эндпоинт — захардкожены.
- MTU/PMTUD-диагностика, трассировка маршрута.
- Async-рантайм — по-прежнему sync + потоки.
